Building Real-Time Pipelines

Building a production-grade streaming pipeline is a complete departure from batch engineering. System changes — a user click, an IoT temperature spike, a financial transaction — are instantly broadcast as individual event objects, typically structured as JSON, Avro, or Protobuf payloads, rather than waiting to land in a daily export. Data is no longer a bounded file with a beginning and an end — it’s an unbounded dataset: a continuous, append-only series of events that never finishes arriving. Producers and consumers stay loosely coupled, talking only through the broker, never directly to each other. To design for that, engineers need to understand what actually happens inside the broker and the processor sitting on top of it.

A minimal streaming pipeline in Python

Before reaching for Kafka itself, it’s worth seeing the same producer / broker / processor shape in miniature. This small simulator swaps Kafka for a plain asyncio.Queue per topic channel:

import asyncio
import json
import random
from datetime import datetime

# Simulating a High-Throughput Distributed Message Broker
class StreamBroker:
    def __init__(self):
        # Different message topic channels
        self.topics = {
            "iot_sensor_stream": asyncio.Queue(),
            "processed_alerts": asyncio.Queue(),
        }

    async def publish(self, topic, message):
        await self.topics[topic].put(message)

    async def consume(self, topic):
        return await self.topics[topic].get()

temperature_sensor_producer emits unstructured readings from two independent sensors, SENSOR_A and SENSOR_B, onto iot_sensor_stream, smoothly and without caring who — if anyone — is reading them. StreamBroker itself handles the concurrent ingress of both streams safely; it doesn’t know or care that two producers are publishing at once, since each call just drops a message onto the appropriate queue. On the other side, anomaly_detection_stream_processor consumes from that same queue and parses each incoming event in real time, running an instant mathematical threshold check and publishing anything that trips it onto processed_alerts — all without ever storing data in an intermediate relational table.

Kafka: partitions, offsets, and consumer groups

A Kafka topic isn’t a single log — it’s split into N ordered, immutable partitions, and every message is routed to exactly one of them. Within a partition, each message gets a monotonically increasing offset, which is simply its address: “message #4,213 in partition 2.”

Consumers read as a consumer group: a set of workers that jointly consume a topic, with every partition assigned to exactly one member of the group at a time. That assignment is what sets the pipeline’s real throughput ceiling — adding consumers beyond the partition count gives zero extra parallelism, because there’s nothing left to hand them.

Concept What it is Why it matters
Partition One ordered, immutable log within a topic Unit of parallelism — more partitions, more concurrent consumers
Offset A message’s position within its partition Lets a consumer say exactly where it is
Consumer group A set of consumers sharing a topic’s partitions Each partition goes to one member only
Offset commit A consumer checkpoints its current position Crash recovery resumes from the last committed offset, not from zero
Rebalance Partition reassignment when a member joins or leaves Keeps the group’s load balanced automatically

Window types: tumbling, sliding, session

A stream never “ends,” so aggregations (sums, averages, counts) need a boundary to close over. That boundary is a window, and the three common shapes solve different problems:

Window type Shape Use case
Tumbling Fixed-size, non-overlapping — every event belongs to exactly one window Hourly sales totals — clean, non-overlapping reporting periods
Sliding Fixed-size, overlapping — one event can appear in multiple windows Rolling 5-minute average CPU load — overlap is needed to catch a spike right at a window boundary
Session Gap-based — the window closes after N seconds of inactivity; size varies per session Click-stream grouping — a user’s session ends after 30+ minutes idle

The lab’s StreamProcessor (in Day2_Lab.ipynb) implements both a tumbling window (one-second buckets, used for a per-second event count) and a sliding window (a rolling 3-second average temperature) side by side over the same event stream, so you can see both update independently as events arrive.

Watermarks: handling late-arriving data

Network delays mean an event timestamped T can physically arrive at the processor at T + 5 minutes. A watermark is a declared threshold that answers “how long am I willing to wait for a late event before I close the window and move on?” — in Spark Structured Streaming:

stream.withWatermark("event_time", "5 minutes")

Anything that arrives after the watermark has already passed is either dropped or routed to a dead-letter side output. The trade-off is direct: a larger watermark buys more completeness at the cost of higher latency; a smaller one returns results faster but drops more late data. Set it from the observed p99 latency of the actual data source — not the theoretical worst case, which would make every window wait far longer than necessary.

Exactly-once delivery — the hard problem

Every streaming system has to pick a delivery guarantee, and the honest options trade off against each other:

Guarantee Behavior Cost
At-most-once Fire and forget Fastest, but silent data loss on failure — never acceptable for financial or audit data
At-least-once Retry on failure No data loss, but duplicates are possible — the most common default
Exactly-once No loss, no duplicates Requires coordination between producer, broker, and consumer

Kafka reaches exactly-once with enable.idempotence=true, the transactional producer API, and isolation.level=read_committed on the consumer side. Flink reaches it with two-phase-commit checkpointing, which only works if the sink itself supports transactions (Kafka, JDBC, Iceberg all do). Either way, exactly-once isn’t free — it adds roughly 20% throughput overhead — so pay for it only where a duplicate would cause real harm (a double-charged payment, a double-counted fraud alert), not for every topic in the system by default.

Ingestion, transformation, orchestration

Every pipeline — batch or streaming — still breaks down into the same three stages; only the tools and latency budget change.

Stage Purpose Typical tools
Ingestion Pull raw data from external systems into central storage Apache Kafka, Debezium, Fivetran, AWS Kinesis
Transformation Clean, filter, and structure the raw data Apache Spark, dbt, PySpark, Pandas
Orchestration Schedule tasks, manage dependencies, handle errors across the whole system Apache Airflow, Prefect, Dagster

Ingestion is the vacuum cleaner gathering raw material — user clicks, database updates, application logs — from wherever it’s generated into central storage. Transformation is the factory turning that raw material into a usable product: filtering out noise, deduplicating records, and converting messy raw files into the standard tables downstream AI models and analytical tools can actually read. Orchestration is the conductor making sure every stage runs in the right order and recovers cleanly when something fails.

Lab: a real-time streaming pipeline with Kafka and Delta Lake

The Day 2 lab notebook puts every concept above into one runnable pipeline, in two parts. It leans on asyncio for the concurrent streaming loops, pins pyspark==3.5.0 alongside delta-spark==3.5.0 to manage the Lakehouse storage sink, and otherwise sticks to the standard library for the math.

Part 1 — mock Kafka streaming pipeline. A MockKafkaBroker (built on asyncio.Queue, with partitions and offsets modeled explicitly) receives readings from three concurrent factory-sensor producers (CNC_MILL_01, ROBOTIC_ARM_02, ASSEMBLY_LINE_03), each flooding the broker independently without talking to each other or locking on any shared thread state. A StreamProcessor consumes them and applies all three concepts from this page at once: a tumbling window (per-second event counts), a sliding window (a 3-second rolling average that keeps readings in memory only for that active span and evicts anything older to keep memory bounded), and a watermark (dropping anything older than 2 seconds). Anything over threshold gets published to an anomalies_sink topic, which a Delta Lake writer appends transactionally, turning the transient micro-batches back into durable, queryable structured logs — the same ACID guarantees from Day 1, now on a live stream instead of a static file.

Part 2 — a real Kafka round trip. The mock broker never touches the actual kafka-python client, and a real capstone pipeline needs schema validation at the edge. This part runs one real KafkaProducer → topic → KafkaConsumer round trip, gated by a Pydantic model (SensorReading) that rejects a deliberately malformed message (a temperature sent as the string "not_a_number") instead of letting it crash the consumer.

Note

Running Part 1’s Delta sink locally on Windows requires a winutils.exe / HADOOP_HOME setup for PySpark — a standard PySpark-on-Windows limitation, not a bug in the notebook (see the same caveat on Day 1). It runs cleanly on Colab (Linux) or macOS/Linux with no extra setup. The notebook’s own saved output for Part 1 was captured from a real executed run on Colab.

Note

Part 2 needs a real, running Kafka broker on localhost:9092 — the notebook includes the commands to start a local single-broker Kafka directly in Colab (KRaft mode, no Zookeeper needed). The output saved in this notebook was captured from a real run against a live broker, and it is the full accept/reject round trip: the producer sends two valid readings and one deliberately malformed one (temperature as the string "not_a_number"), and the consumer accepts the two valid readings, rejects the malformed one on SensorReading’s validator, and ends with Summary: 2 accepted, 1 rejected by the schema gate. If you run this cell without a broker running, you’ll see a connection failure instead — the schema-gate code catches that case and prints clear setup instructions rather than a raw stack trace, but that’s not what the saved output here shows.
